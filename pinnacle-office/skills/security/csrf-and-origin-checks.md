# CSRF and origin checks

What the security specialists in this seat have learned working on Pinnacle AI.
- api/chat.ts already has the exact IP-extraction and sliding-window rate-limit pattern (x-vercel-forwarded-for over x-forwarded-for) reused here verbatim, so any future per-IP throttle in this repo should copy that same clientIp/isRateLimited shape rather than reinvent it.
- streamLLM in api/_llm.ts only accepts a single reminder string, not a list of trailing system messages, so the non-overridable guard has to be concatenated onto the client reminder rather than injected as a separate message — worth knowing before anyone tries to add a second trailing system slot there.
- body.system is still 100% client-controlled after this change; the guard neutralizes a hijacked system prompt by out-ranking it via recency, it does not restrict what system can say. If a future task wants to lock down system too, that touches api/_llm.ts, which was out of scope here.
- The orphan-identity guard described in this task is already implemented verbatim in the current src/lib/cloud.ts (linkError check at line 88), so future tasks referencing this exact symptom should first diff against git history to confirm it wasn't already landed before assuming work is needed.
- The resource shape only has url as an optional field on some items (schoolId is also optional/nullable), so the validator treats a missing url as valid rather than rejecting it — only a present-but-bad-scheme url fails.
- state.ts and resources.ts had no clientIp() helper at all before this — they were rate-limiting only by verified user id, meaning an unauthenticated flood of invalid tokens hit zero throttling in either file prior to this change, not just a weak one.
- state.ts and resources.ts's isRateLimited() previously hardcoded RATE_LIMIT_MAX with no max parameter at all, unlike chat.ts and master-login.ts which already took one — had to add the parameter to both the RPC-backed and in-memory-fallback helpers before a second ceiling could be threaded through.
- The four isSameOrigin() copies were byte-identical including comments, so this was a pure find-replace across chat.ts/state.ts/resources.ts/master-login.ts with no per-file variation to worry about. netlify/functions/chat.mts also has its own isSameOrigin at line 32 but it was not in the files-in-scope list, so it's left with the old AND-both-required behavior and will need the same fix later.
- The three 'wip: edits made outside the office' commits at the top of master (5b2324b, 3f01c2b, 6bce34e) already contain substantial security work including this exact task — check git log on files-in-scope before assuming a task is unstarted, since work parked outside the office can silently pre-empt an assigned task.
- verifiedAdmin() reads school_id from app_metadata, not user_metadata, and that's deliberate — app_metadata can only be set with the service-role key, so a student/admin can never self-grant another school's scope by editing their own profile. Don't 'fix' this to match a task description that says user_metadata.
- POST's upsert() on `id` is the actual IDOR surface here, not GET/DELETE — an upsert with a foreign but existing id silently takes ownership of that row unless you check existing school_id first. Any future write path added to this file needs the same existing-row ownership check before upserting.
- schema.sql's on_auth_user_deleted trigger already exists and fires on any auth.users delete regardless of who calls it (dashboard or admin.deleteUser API), so a self-serve delete route needed zero schema changes, just the verified-identity gate on the API side.
- GET and POST in api/resources.ts were already correctly school-scoped before this task started (school_id from app_metadata, POST ownership check on existing rows, forced school_id on write) — only check DELETE's actual match count before assuming a task like this is unstarted.
- Supabase's delete() reports success (no error) even when the eq() filters match zero rows, so a school-scoped delete on a foreign id silently no-ops and returns 204 unless you .select() the deleted rows and check the returned array length yourself.
- chat.ts's IP rate-limit only runs when supabaseUrl && supabaseServiceKey are both set, so with Supabase unconfigured there is no IP throttle at all on that route — matches verifiedUserId's own undefined-when-unconfigured behavior, not a gap worth flagging unless someone changes that bypass logic later.
- delete-account.ts's own RATE_LIMIT_MAX (5/min) is a per-IP cap using the default max param; the new global cap had to be a separate named constant passed explicitly since isRateLimited's default max is RATE_LIMIT_MAX, not GLOBAL_RATE_LIMIT_MAX — same shape as api/state.ts.
- Supabase auth-js v2.47 exposes a stable error.code ("email_exists") on the AuthApiError for this exact case, confirmed in node_modules/@supabase/auth-js/src/lib/error-codes.ts — no need to string-match error.message, which is more fragile and can change with locale/version.
- rate_limit_hit() in supabase/schema.sql is revoked from public and granted only to service_role, so any new rate-limited endpoint must use the service-role client for the RPC call even if the underlying operation (like signInWithPassword) would work fine on the anon key.
- cloud.ts's authToken() still calls supabase.auth.signInAnonymously()+updateUser() directly for the first-ever-sync identity-linking path — that's a different call from password sign-in and was left untouched as out of scope for this task.
