# prompt architecture

What the tutor specialists in this seat have learned working on Pinnacle AI.
- Bash permission enforcement in this sandbox is stricter than the 'node scripts/*' allowlist described in the task brief: running a brand-new script under scripts/ hung on 'requires approval' with no way to grant it, and rm was flatly denied. Don't count on ad-hoc node scripts for verification here; typecheck + manual regex tracing was the fallback.
- numbers()/qNums treats every digit sequence in the question as a candidate 'already given' value, including exponents like x^2 — any future numeric-parsing change in grade.ts should keep exponents excluded from that set or the same shadowing bug reappears in a different form (e.g. x^3 with a root of 3).
- Curriculum chapter ids and NCERT chapter ids share the same scheme (e.g. c10-maths-01), so a lesson's map.chapterId is a valid direct key into both ncertChapterById and a curriculum SUBJECTS scan without any translation step.
- findNcertForQuery (in src/data/ncert/index.ts, out of this task's scope) only accepts one classLevel at a time, so entrance-mode NCERT lookup in groundingFor now calls it once per class level (11 then 12) and takes the first hit rather than that function being made multi-level aware itself.
- groundingFor was already entrance-aware (classLevelsFor helper exists and is exported-in-module already) but groundingForChapter, used whenever a lesson plan grounds on a known chapterId rather than a fuzzy text search, still took only a single classLevel and had no mode param at all — the two grounding paths had drifted apart. Check both whenever this kind of scoping bug is filed again.
- Full class 11+12 title text for entrance modes runs close to 4000 chars raw (title strings alone measured at 2100 and 1831 chars for class 11 and 12 respectively, before subject-name headers) — if a future curriculum expansion pushes this over the cap, the truncation cuts at a subject-line boundary and appends '…(list capped)', so it degrades gracefully rather than mid-sentence.
- pushChat for the assistant's reply happens BEFORE advance() runs, so lesson.phase in state is always the NEXT phase to run, not the phase the just-shown reply was for — any quick-reply/UI logic keyed off lesson.phase has to account for that lag, not just the teach case.
- The same reply-lags-phase pattern also affects check -> reteach (planCheck's wrong-answer reply already gives a hint and re-asks smaller before the real reteach explanation exists), which reads like the same bug class but wasn't in this task's scope.
