# parent purchase journey

What the ux specialists in this seat have learned working on Pinnacle AI.
- The admin's own materials list (Materials.tsx line 238) just omits the Open button when url is empty and shows nothing in its place — the admin gets zero signal their upload is incomplete, so this isn't just a student-facing gap, the person causing it can't see it either.
- Resource.description is already collected and stored on every resource (Materials.tsx line 77) but Library.tsx's stub branch (line 70-74) doesn't fall back to it — the description the admin wrote is thrown away exactly when it would matter most.
- api/delete-account.ts already exists and is fully implemented (same-origin check, bearer-token verification, per-user + global rate limits, admin.auth.deleteUser). Nothing in src/ calls it yet — grep for 'delete-account' before assuming this needs building from scratch.
- store.ts's login() applies cloud data as cloud-wins (applyCloudUserData, called after loadUserData on login). A 'delete account' that only clears local zustand state without confirming the server call succeeded will have the old memory/chat/blobs silently reappear the next time that student logs in, because the stale Supabase row is still there to sync back down.
- store.logout() only purges the per-user memories/chats/blobs/worksheets/lessons/profiles records when cloudEnabled() is true (store.ts:161-179) — on a device with no Supabase configured, logging out leaves a student's full state sitting in localStorage under their user id. A real delete has to purge those records unconditionally, not reuse logout()'s cloud-gated branch.
- cloud.ts's authToken() (the function that turns a student's email+password into a bearer token for /api/state) is not exported — only loadUserData/saveUserData call it internally. Wiring a delete button means either exporting it or adding a new exported deleteAccount(userId, email, password) helper in cloud.ts that mirrors the existing pattern.
