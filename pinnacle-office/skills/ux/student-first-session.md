# student first session

What the ux specialists in this seat have learned working on Pinnacle AI.
- Both buttons call the same underlying action (clearChat from useStore) that wipes tutor conversation history — Tutor.tsx additionally resets genRef/abortRef/lesson state, so a fix can't just swap in Profile's handler wholesale, it needs to keep newSession()'s cleanup and only gate the clearChat() call behind confirmation.
- The Modal component already exists and is imported in Profile.tsx from ../../components/ui — reusing it in Tutor.tsx would be a small, consistent fix, not a new pattern.
- The default password isn't cosmetic: Students.tsx:76 calls linkCloudProfile which does supabase.auth.updateUser({password: u.password}), so whatever sits in the field when admin clicks submit becomes that student's real Supabase Auth password, not just local mock state.
- Login.tsx has two password-check paths (local extraUsers plaintext compare via login(), and supabase.auth.signInWithPassword when cloud is enabled) — a fix to Students.tsx only touches what password is generated, not how it's later verified, so it's safe to scope narrowly.
- The codebase has zero existing crypto.getRandomValues usage; all present randomness (Math.random) is for three.js/visual seeding, so a password generator would be the first cryptographically-secure RNG call in the repo — worth flagging in review since it's a new pattern, not an oversight.
- Chapter.tsx's saveProgress lets status and confidence move independently (separate <select> and <input type=range>), so 'Mastered' can be set while confidence sits wherever the slider was last left (including 0 if never touched) — assessChapter's design deliberately forecloses this by tying each status button to one fixed confidence value.
- lib/mastery.ts's chapterMastery formula: score = round(STATUS_BASE[status]*0.55 + confidence*0.45), STATUS_BASE.mastered=92 — at confidence 0 that's 50.6→51, which masteryBand() classifies 'shaky' (score<55) despite status='mastered'. This is the precise mechanism behind the Chapter/Planner mismatch the task describes.
- Students.tsx's 'Add student' form silently cannot reset an existing student's password: submit() checks allUsers().some(email match) and bails with 'that email already has an account' before addStudent/linkCloudProfile ever runs. There is no per-row reset action in the roster table. Today, a locked-out student has no recovery path at all, self-serve or admin.
- Self-serve reset is cloud-only by construction: with cloudEnabled() false there is no email-sending path in this codebase, so a school running without Supabase configured needs a different (non-self-serve) answer, not a hidden/broken button.
