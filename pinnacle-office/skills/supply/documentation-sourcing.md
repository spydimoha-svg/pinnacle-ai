# documentation sourcing

What the supply specialists in this seat have learned working on Pinnacle AI.
- TOOLS.build already contains Bash(node scripts:*) in pinnacle-office/core/claude.mjs:36, and it is granted to every dept.kind === 'code' department (Tutor Engine included, org.mjs:55) whenever state.office.mode === 'apply' (default per config.mjs:51). Do not re-source this as if it were missing without first checking the office's mode at the time of the failure.
- Bash(rm:*) is explicitly in the permission deny list at claude.mjs:26. In Claude Code's permission model deny always wins over allow, so no tool-list change can grant rm without editing that line, and pinnacle-office/core/ is itself on the forbidden-paths list in config.mjs, so no agent, Supply included, can make that edit anyway.
- The clean pattern for any future script that needs scratch files: write and delete them from inside the Node script itself with fs.unlinkSync/fs.rmSync. That runs inside the already-approved 'node scripts/*.mjs' process and needs zero extra Bash permission.
- WebFetch's summarizer sometimes refuses a literal-verbatim request citing copyright and offers a paraphrase instead, so a single WebFetch call is not proof, even with a URL attached, it needs an independent WebSearch corroboration on the same date claim before you write it down as verified, especially after a prior memo in this exact file was already flagged as fabricated.
- Cerebras' public model catalog (inference-docs.cerebras.ai/models/overview) does not list any llama-3.3 variant at all today, it's gpt-oss-120b, gemma-4-31b, zai-glm-4.7 only, but third-party tracker sites (free-model.com, freellm.net) still advertise llama-3.3-70b as available on Cerebras' free tier, likely stale. Trust the provider's own docs page over aggregator sites when they conflict.
- GROQ_FALLBACK_MODELS defaults to "openai/gpt-oss-120b,llama-3.1-8b-instant" (api/_llm.ts:121). The first fallback is healthy but the second, llama-3.1-8b-instant, is on Groq's own deprecation list for the same 2026-08-16 shutdown date as the primary model DEFAULT_MODEL.groq. After that date the groq leg narrows from 3 candidate models to 1 (gpt-oss-120b) unless the env var is updated first.
- onnxruntime-node alone is 270.8MB unpacked, already over Vercel's 250MB standard limit before piper-plus or any model file is added — that path is a hard no on Hobby regardless of which model is chosen, confirmed rather than assumed.
- @playwright/mcp ships --ignore-https-errors and --allowed-origins/--blocked-origins flags specifically for this kind of case, but --allow-unrestricted-file-access and --no-sandbox exist too, so scope the MCP config narrowly (headless, restrict to the specific gov domain via --allowed-origins) rather than installing it wide-open.
- The model itself is real: ai.google.dev/gemini-api/docs/models/gemini-3.6-flash exists and confirms the model ID string 'gemini-3.6-flash', and ai.google.dev/gemini-api/docs/pricing confirms free-tier input/output tokens are 'free of charge' with paid tier priced at $1.50/$7.50 per 1M tokens. Neither page states a rate limit number.
- Third-party aggregator sites (aifreeapi.com, tokenmix.ai, bswen.com) all claim specific Flash-tier numbers but contradict each other (10 RPM/250K TPM/1500 RPD vs 15 RPM/1M TPM/1500 RPD), consistent with the existing pdf-reader-mcp memory pattern: don't trust these without independent corroboration from the provider, and right now the provider gives no corroboration to check against.
- qwen/qwen3.6-27b is Groq's other recommended replacement for llama-3.3-70b-versatile but it's flagged 'preview' status ('intended for evaluation purposes only... should avoid production'), so it's not a safe pick for a student-facing tutor even though it appears on the same recommendation line as openai/gpt-oss-120b.
- openai/gpt-oss-120b is already the first entry in the current GROQ_FALLBACK_MODELS default. If it becomes DEFAULT_MODEL.groq too, the fallback list needs the duplicate removed or the chain wastes a retry hitting the same model twice.
- npm audit is bundled with npm itself (confirmed on docs.npmjs.com/cli/v11/commands/npm-audit), so there is no npm install command to source for it, the task is really a permission-list change, not a procurement one.
- Bash(npm audit:*) is unsafe as a grant: the pattern is a raw prefix match, so it would also match 'npm audit fix', 'npm audit fix --force', and 'npm audit signatures', all of which mutate package.json/package-lock.json or hit registry write paths. The safe grant is exact-match strings only, following the same pattern claude.mjs already uses for 'gh auth status' at line 98.
- npm audit's network call is a POST to the registry's /-/npm/v1/security/advisories/bulk endpoint. This is the same class of registry network access TOOLS.survey already grants via 'npm view:*', so adding audit does not open a new category of network reach for this seat, just a new read-only registry query.
- Write(./pinnacle-office/**) is also explicitly denied at claude.mjs:41, so 'a shared drop location' inside pinnacle-office is blocked the same hard way as curl, not just unconfigured.
- src/data/questions already encodes the content team's actual sourcing discipline: every question is tagged pyq/important/exemplar/sample rather than fabricating a paper year, and mark/type follows the real CBSE 1=mcq,2=vsa,3=sa,4=case-based,5=la mapping. Any content reference handed to that team should reinforce this discipline, not just be a raw NCERT PDF link.
- core/claude.mjs and config.mjs are both on the forbidden-paths list (config.mjs:139) and Write/Edit-denied for every agent (claude.mjs:56-57), so even if granting install execution were the right call, no Supply specialist could make that edit themselves, this has to be a manual change by Ayaan.
- catalog.md as it stands has zero variety, not partial duplication, every one of its six lines is byte-identical. Whatever process appends an entry per answered request (mentioned in the queue-hygiene memory) is not checking for an existing identical line before appending, that's the root cause worth fixing upstream, not just this one cleanup.
- TOOLS.docs in core/claude.mjs (line 134) is the ground truth for what readdoc can do: Bash(readdoc:*), Bash(command -v readdoc), Bash(which readdoc). Nothing else. The catalog's description ('PDF and text to plain text with page numbers. Local, free, reads only.') matches this exactly, so no correction needed to the description text itself.
- Even a dept.kind change wouldn't be enough: claude.mjs:56-57 denies Write(./pinnacle-office/**) in both relative and absolute form for every spawned agent regardless of department, and the file's own comment says deny always beats allow in Claude Code's permission model -- so a narrower allow for just catalog.md would sit underneath that deny and do nothing until the deny itself is edited.
- The same package that reads plan tier also ships `vercel buy` (credits, pro upgrade, domains) -- a genuinely money-spending command living in the same binary. Any future task that authenticates this CLI in an automated context must scope the token narrowly or restrict which subcommands can run, since a read-only need (plan lookup) shares a binary with a real-money command.
- console.groq.com/docs/deprecations gave the exact same date (2026-08-16 shutdown, 2026-06-17 announcement) on a direct WebFetch and an independent WebSearch, so that specific claim is now confirmed twice over, not just once.
- ai.google.dev's own model page and deprecations page disagree with each other and with third-party coverage on what to migrate gemini-2.0-flash TO — one fetch said gemini-3.6-flash, another synthesis said gemini-2.5-flash. The 'it's dead' fact is solid across three independent checks; the replacement pick is not and needs its own verification pass before anyone hardcodes it.
- read_only and project_ref are URL query params on the hosted endpoint, not CLI flags (?project_ref=<ref>&read_only=true). project_ref scopes the server to one project and removes account-level tools (list_projects, create_project); read_only runs execute_sql as a read-only Postgres role and disables every mutating tool (apply_migration, deploy_edge_function, storage/branch writes).
- The project ref for this Supabase project is not in the repo anywhere (checked VITE_SUPABASE_URL usages, README, LAUNCH.md) — it only exists as an env var value Ayaan holds, so he has to fill in the URL himself before this is usable, Supply cannot source it from the codebase.
