Pinnacle Cinematic Architecture

The sixteen-part proposal the specification asks for, written against the codebase as it actually stands today. No destructive changes have been made — §39 asks for validation first, and this is that request. The headline finding: Pinnacle already has the cinematic language and most of the narrative intelligence. Both stop at the login screen.

The central finding

You are not starting from zero — you are closer than the spec assumes. src/pages/Landing.tsx is already a six-chapter WebGL descent with three shader scenes. src/lib/lesson.ts is already a deterministic director: it decides pacing phase by phase and explicitly refuses to let the model choose when to move on. src/data/concepts/types.ts already carries Prereq.probe and leadsTo — which are the flashback (§11) and foreshadowing (§12) systems, sitting in the data model unused by the UI.

So the work is not inventing these systems. It is carrying the cinematic language across the login boundary and surfacing intelligence that is already computed and currently rendered as cards.

01

Product architecture

Four layers, strictly separated so the cinema never becomes load-bearing for the teaching. This is the constraint that makes §31 (accessibility) achievable rather than aspirational: every layer below the Stage is fully functional with the Stage switched off.

StageWebGL worlds, motion, sound. Entirely optional.
DirectorDeterministic. Chooses scene, pacing, branch.
IntelligenceLearner profile, mastery, memory, grading.
Ground truthNCERT, concept graph, question bank.

The single most important architectural decision in this document: the Director is code, not a model call. §9 describes the AI choosing scene, pacing, camera, difficulty and branch. Implemented as an LLM call per beat, that is roughly nine extra calls per scene — unaffordable on the token budget, and unreliable on the small free models the app falls back to. lesson.ts already proves the alternative works. The model writes prose; the app decides structure.

03

Cinematic interaction model

A Scene is the atomic unit. It is a typed object, not a page, and it composes from beats. The nine-scene arc in §7 of the spec is a template over these beats, not a hard sequence — the Director assembles the arc per student. 

Beat = setup | reveal | predict | experiment
     | respond | formalise | check | diagnose | transition

Scene {
  conceptId    // anchors to the existing concept graph
  beats        // ordered, but skippable per learner
  stage        // which world + which interactive object
  exitCriteria // what proves this scene landed
}

Three interaction laws, each falsifiable in review:

  • The student moves first where possible. A predict beat precedes every reveal beat. This is what makes the student the protagonist (§2) structurally rather than tonally.
  • The interface carries part of the explanation. If a reply can be a manipulable object or a diagram, it must not be a paragraph (§20).
  • Exam mode inverts everything. §22 is not a compromise — it is a designed contrast. The absence of cinema is what makes a Trial feel like a trial.
04

AI architecture

Preserve the existing chain and add one layer. api/_llm.ts already satisfies §34 completely — six interchangeable providers, priority-ordered, with automatic failover and no vendor lock-in. Nothing about model agnosticism needs building; it is done. 

Student action
   ↓
Director            deterministic — src/lib/director.ts (new)
   ↓ selects beat + branch from learner profile & mastery
Beat prompt builder  one small job per call, as lesson.ts does today
   ↓
_llm.ts chain       Gemini → DeepSeek → Groq → local
   ↓
Response shaper     prose | figure spec | 3D scene | check question
   ↓
Stage renders; grade.ts marks; Director chooses the next beat

Grading stays mechanical wherever it can be. grade.ts settles numeric and keyword answers exactly, for free, identically on every model — and that determinism is precisely what §17's "misconception detected" needs. You cannot diagnose a root cause from a model that is guessing whether the answer was right.

05

Knowledge architecture

The graph exists. Concept already has needs, mistakes, figure, check and marks; Prereq already has a probe question with a stored answer. §13's knowledge universe is a rendering of data the app already computes.

Flashback · §11

Already possible. concept.needs → prereq.probe gives a real question with a stored answer. The UI has never shown it.

Foreshadowing · §12

leadsTo is in the type and largely unpopulated. Needs content authoring, not engineering.

Node decay · §28

mastery.ts already models spaced-repetition decay with per-status staleness. Drives the fading node directly.

Graph render

cytoscape is already a dependency and already in the bundle. Use it for the 2D universe; do not build a 3D graph.

The real constraint — read this twice

There are 274 curriculum chapters, 8 authored concept maps, and 13 verbatim NCERT chapters. Everything else derives its map from chapter key-topics, and derived maps carry authored: false — no stored check answers, no worked examples. A cinematic scene needs authored ground truth to be worth watching.

This is a content problem wearing an engineering problem's clothes, and it is the single largest risk to the vision. The architecture below is deliverable in weeks. Covering the syllabus at this quality is a multi-year authoring programme. Plan the product around depth in a few journeys, not breadth across all of them.

06

Student-memory architecture

Three stores exist and are well-shaped. One is missing.

StoreHoldsStatus
LearnerProfileModality preferences, pitch level, interests, recurring habitsPreserve Exactly what §10 branching needs.
StudentMemoryClass, mode, streak, altitude, per-chapter progressPreserve
LessonStatePhase, concept index, gaps, retries, reteachesExtend → SceneState
StudentStoryTimestamped narrative beats: discoveries, misconceptions, breakthroughsNew The raw material for §24 and flashbacks.

Storage warning. The Zustand store persists to localStorage under a shared ~5 MB quota. A per-beat story log will exceed it within a term. StudentStory must be capped and rolled to Supabase, with only a recent window kept locally — the same discipline already applied to the OSM console's scanned pages.

07

Frontend architecture

Stay on React + Vite + React Router. Do not migrate to Next.js. §32 asks for the simplest architecture capable of the experience, and §34 warns against fashion. Pinnacle is an authenticated SPA with no SEO surface behind the login and no server-rendering requirement; a framework migration would consume the entire budget for zero user-visible gain. The landing page — the one public surface — already performs well as a static build.

The one structural change that matters:

<App>
  <WorldCanvas />   ONE WebGL context, mounted once, never unmounted
  <DirectorProvider>
    <Routes />       DOM chrome only — text, controls, dialogue
  </DirectorProvider>

Scene changes swap uniforms and camera targets on the persistent canvas; they do not mount and unmount renderers. Browsers cap live WebGL contexts at roughly 8–16, and a router that creates a context per scene will silently lose the earliest ones — a class of bug that appears only after a student has explored for a while, which is the worst time to find it.

08

Animation and rendering strategy

Every animation dependency the vision needs is already installed and already proven on the landing page: gsap, motion, lenis, three, @react-three/postprocessing, @paper-design/shaders-react. Add nothing.

TierDetected byRendersStory intact?
Tier 2 — Fulldesktop + WebGL2Shader worlds, postprocessing, particles, 3D objectsYes
Tier 1 — Leanmobile / integrated GPU3D objects only, no postprocessing, CSS transitionsYes
Tier 0 — Stillreduced-motion, no WebGLStatic figures, instant state changes, full textYes

Tier 0 is not a degraded build. Under prefers-reduced-motion, GSAP timelines collapse to their end state rather than being removed — every reveal still happens, instantly. A student who needs reduced motion gets the same narrative, not a worse product.

Motion must encode meaning (§28). The test: if an animation can be deleted without the student losing information, delete it.

10

First vertical slice

Conflict — the chosen prototype has the least ground truth

§38 specifies Physics / Newton's Laws. All eight authored concept maps are Mathematics; the verbatim NCERT set is Class 9–10 Maths and Class 10 Science. There is no authored concept map for Newton's Laws. Building the slice there means authoring that ground truth first — roughly a week of content work before the first scene can be honest.

Two options. (a) Author it — keeps the spec's subject, costs a week upfront, and Physics is undeniably the better showcase for a cinematic world. (b) Slice on Class 10 Quadratic Equations — authored map, verbatim exercises and worked answers all exist today, so engineering starts immediately. My recommendation is (a), because the vision is a Physics vision and proving it on algebra would undersell it — but the week must be scheduled, not discovered.
